The Stitch Architecture Book

Introduction: The Stitch Ecosystem

Welcome to The Stitch Architecture Book, the comprehensive technical manual for building extreme-throughput, zero-allocation data processing pipelines and low-latency network applications in Rust.

1. The Core Problem: The Modern Systems Tax

Modern network services and real-time processing engines suffer from accumulated latency layers:

  • Dynamic Dispatch Overhead: Trait objects (Box<dyn Layer>, Box<dyn Service>) introduce indirect vtable lookups, instruction cache misses, and inhibit inline compilation.
  • Heap Allocation Jitter: Unbounded object allocations (Vec<u8>, String, heap-allocated messages) trigger global memory allocator contention and non-deterministic GC pauses or page faults.
  • Serialization Redundancy: Common interchange formats (JSON, schema-heavy Protobuf) spend precious CPU cycles traversing complex pointer graphs, copying bytes, and executing variable-length zigzag decoders.
  • Memory Subsystem Abuse: Cache lines (64 bytes on modern x86_64/ARM64 architectures) are frequently straddled or underutilized due to arbitrary field reordering and memory padding holes.

2. The Stitch Solution: Unified Architecture

The Stitch architecture addresses these challenges across three foundational layers:

3. Core Architectural Invariants

Throughout this book and codebase, four invariant rules are strictly enforced:

  1. #![no_std] Foundations: Core crates (stitch-core, stitch-wire-core, stitch-data-core) do not depend on the standard library or dynamic memory allocation.
  2. Deterministic Latency: No hidden allocations on the hot path. All scratch spaces and ring buffers are statically sized or caller-allocated.
  3. Mechanical Sympathy: Physical memory layouts are engineered directly around hardware cache lines (64 bytes).
  4. Explicit Failure: No silent error suppression, truncation, or dummy fallbacks. All boundary errors are represented as typed domain results.

The “Scrooge” Systems Mindset

In the Stitch ecosystem, every architectural decision is guided by the “Scrooge” Systems Mindset — a philosophy of pathological zero-waste and mechanical sympathy.

1. Zero Waste: Every Byte and Cycle Counts

Modern hardware executes billions of cycles per second, yet high-level abstractions routinely waste more than 90% of effective memory bandwidth on cache misses, pointer indirections, and allocator locks.

The Scrooge mindset rejects lazy engineering habits:

  • Cache Line Straddling: On x86_64 and ARM64 CPUs, cache lines are 64 bytes wide. If a frequently read data structure occupies 68 bytes or crosses a 64-byte boundary unaligned, every memory access forces two separate L1D cache line fetches instead of one.
  • Padding Holes: Structs without explicit field ordering often contain invisible padding bytes introduced by compiler alignment rules. In Stitch, fields are ordered descending by alignment or packed cleanly (#[repr(C)]).
  • Pointer-Chasing Graphs: Heap-allocated node graphs (such as linked lists, boxed closures, or nested Vec containers) scatter memory addresses across DRAM. Stitch prioritizes flat, contiguous memory slices (zerocopy, contiguous ring buffers, columnar slabs).

2. Monomorphism Over Polymorphic Indirection

Dynamic dispatch (dyn Trait) creates three performance penalties:

  1. An extra memory read to fetch the vtable pointer.
  2. An indirect branch instruction (call rax), which frequently defeats hardware branch target predictors (BTB).
  3. Complete defeat of compiler optimization: the LLVM optimizer cannot inline functions across dynamic trait objects, eliminating dead-code elimination, vectorization, and register promotion.

Stitch replaces dynamic trait objects with monomorphic compile-time composition:

#![allow(unused)]
fn main() {
// ANTI-PATTERN: Heap-allocated polymorphic pipeline
let pipeline: Vec<Box<dyn Layer>> = vec![
    Box::new(DecompressLayer),
    Box::new(ValidationLayer),
];

// STITCH PATTERN: Monomorphic zero-cost static pipeline
let pipeline = Pipeline::new()
    .with(DecompressLayer)
    .with(ValidationLayer);
// Inlines directly into linear machine code without indirect jumps.
}

3. Lossless Correctness Contracts

A common pitfall in high-throughput systems is introducing lossy heuristics (such as truncating identifiers, dropping low-order bits, or coalescing updates) into default paths.

In Stitch:

  • Default configurations are strictly lossless and 100% correct.
  • Any lossy optimization (such as coordinate quantization or floating-point truncation) must be an explicit, contractually specified opt-in flag.
  • Over-approximation boundaries must be provably bounded and covered by unit tests.

4. Speculative Complexity & YAGNI

Never introduce complex, unproven data structures (like Eytzinger BFS arrays, succinct Elias-Fano, or multi-level radix trees) based solely on synthetic microbenchmarks.

Real production workloads are dominated by cache pollution, kernel boundaries, and memory bandwidth. If 20 lines of idiomatic, cache-aligned Rust or linear SWAR scanning outperforms a complex theoretical structure, choose simplicity. Always measure end-to-end latency with statistical rigor.

Foundations & The U-Cycle Lifecycle

The Sewing Machine Architecture (SMA) is the architectural pattern that powers stitch-core. It treats data processing as a physical stitch needle piercing cleanly through a stack of fabric layers and returning back up in a bounded U-cycle.

1. The Anatomy of a Stitch

Traditional middleware architectures (like tower or axum) rely on asynchronous futures or recursive closures (next(req)), which allocate memory or produce complex state machines that cannot be fully flattened by compiler optimizers.

SMA decomposes processing into two strictly bounded phases:

  1. Descent (on_enter): The needle pierces downward through ordered pipeline layers. Each layer inspects, validates, or mutates the shared blackboard context.
  2. Terminal Execution (TerminalHandler): The needle reaches the lowest point of the stroke, where the core domain logic or state transition executes.
  3. Ascent (on_exit): The needle ascends back upward through the layers in reverse topological order. Layers perform post-processing, metric recording, or cleanup.
    Down (Descent)                           Up (Ascent)
         │                                        ▲
         ▼                                        │
  ┌──────────────┐                         ┌──────────────┐
  │ Layer 1      │ -- on_enter() ------->  │ Layer 1      │ -- on_exit()
  └──────┬───────┘                         └──────▲───────┘
         │                                        │
         ▼                                        │
  ┌──────────────┐                         ┌──────────────┐
  │ Layer 2      │ -- on_enter() ------->  │ Layer 2      │ -- on_exit()
  └──────┬───────┘                         └──────▲───────┘
         │                                        │
         └─────────────► ┌────────────────┐ ◄─────┘
                         │ Terminal Target│
                         └────────────────┘

2. The Monomorphic Layer Contract

In stitch-core, every layer implements the Layer trait:

#![allow(unused)]
fn main() {
pub trait Layer<C: ?Sized> {
    /// Executed during needle descent.
    /// Returns FlowControl to determine whether descent continues.
    fn on_enter(&mut self, context: &mut C) -> FlowControl;

    /// Executed during needle ascent in reverse pipeline order.
    fn on_exit(&mut self, context: &mut C);
}
}

Because the traversal order is resolved at compile time, the compiler completely eliminates recursion and call-stack growth, inlining both passes into a straight sequence of instructions.

Monomorphic Pipelines vs Dynamic Dispatch

Dynamic dispatch is the silent performance killer of low-latency systems. This chapter demonstrates how stitch-core achieves zero-cost pipeline composition through compile-time type-level nesting.

1. Type-Level Composition (PipelineStack)

Instead of storing layers in a slice of trait objects (Vec<Box<dyn Layer>>), stitch-core uses a recursive cons-list structure at the type level:

#![allow(unused)]
fn main() {
pub struct LayerCons<H, T> {
    pub head: H,
    pub tail: T,
}

pub struct LayerNil;
}

When you chain layers using the fluent builder API:

#![allow(unused)]
fn main() {
let pipeline = PipelineBuilder::new()
    .with(RateLimitLayer::new(100_000))
    .with(AuthValidationLayer)
    .with(ChecksumLayer)
    .build(TerminalCore);
}

The resulting pipeline type is concrete and fully known to the Rust compiler:

#![allow(unused)]
fn main() {
Pipeline<
    LayerCons<RateLimitLayer,
        LayerCons<AuthValidationLayer,
            LayerCons<ChecksumLayer, LayerNil>>>,
    TerminalCore
>
}

2. Zero-Cost LLVM Inlining

Because there are no trait objects or vtables:

  1. The compiler monomorphizes the entire descent (on_enter) and ascent (on_exit) sequence.
  2. If a layer’s on_exit method is empty (the default no-op implementation), LLVM completely removes the function call and branch during dead-code elimination.
  3. Intermediate registers are preserved across layer boundaries instead of being spilled to the stack to comply with standard C calling conventions.
  4. Hot loops processing thousands of packets achieve performance identical to hand-written, monolithic assembly code.

Zero-Allocation Flow Control & Blackboards

In high-throughput systems, returning Result<T, E> through deeply nested handler stacks often incurs heap allocation (via Box<dyn Error>) or bloats enum return registers across call boundaries.

SMA solves this through two complementary constructs: Zero-Allocation FlowControl and the Blackboard Pattern.

1. FlowControl Primitives

FlowControl is a compact enum that instructs the SMA needle driver how to proceed during descent:

#![allow(unused)]
fn main() {
#[repr(u8)]
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum FlowControl {
    /// Continue downward descent to the next layer or terminal handler.
    Continue = 0,
    /// Immediately abort downward descent and begin ascending (U-turn).
    Break = 1,
}
}

Because FlowControl is represented as a single byte (#[repr(u8)]), it is returned directly in a CPU general-purpose register (e.g. AL on x86_64) without stack writes.

Early Short-Circuiting (The U-Turn)

When any layer encounters an invalid condition (e.g., rate limit exceeded or invalid signature), it returns FlowControl::Break:

  1. The needle immediately ceases descent; subsequent downstream layers and the terminal handler are skipped.
  2. The needle ascends back through all layers that have already executed on_enter, invoking their on_exit handlers.
  3. This guarantees that any acquired state, transaction counters, or metrics are strictly and deterministically unwound without memory leaks.

2. The Blackboard Pattern

Rather than passing payloads as values that move across function arguments, SMA adopts the Blackboard Pattern.

A single mutable reference (&mut Context) is passed down and up the pipeline:

#![allow(unused)]
fn main() {
pub struct RequestBlackboard {
    pub raw_bytes: [u8; 1500],
    pub payload_len: usize,
    pub client_id: u32,
    pub is_authenticated: bool,
    pub execution_status: u16,
}
}

All layers operate in-place upon this memory region. This ensures:

  • Zero Allocations: Memory is allocated once (on the thread stack or pre-allocated ring buffer).
  • Cache Warmth: The blackboard stays resident in the CPU L1 data cache throughout the entire duration of the stroke.

Cache-Line Engineering & 64-Byte Alignment

Hardware memory subsystems do not read individual bytes from DRAM; they fetch chunks of 64 contiguous bytes known as cache lines.

When an access spans across two cache lines, or when two CPU cores write to independent fields located within the same 64-byte line (false sharing), latency increases dramatically.

1. The 64-Byte Invariant

In the Stitch ecosystem, hot blackboards, headers, and ring buffer slots are aligned to 64 bytes using #[repr(C, align(64))]:

#![allow(unused)]
fn main() {
#[repr(C, align(64))]
pub struct OrderBookBlackboard {
    pub symbol_id: u32,
    pub sequence: u64,
    pub best_bid: u64,
    pub best_ask: u64,
    pub bid_qty: u32,
    pub ask_qty: u32,
    pub flags: u16,
    pub _reserved: [u8; 30], // Pads exactly to 64 bytes
}
}

Why Exact Alignment Matters

  1. Single Cache-Line Access: A 64-byte aligned struct is guaranteed to fit entirely within a single L1D cache line. Any read or write hits the same cache block.
  2. Elimination of False Sharing: In multi-threaded worker pools, aligning per-core blackboards or ring buffer queues prevents false sharing cache invalidations between CPU cores.

2. Compile-Time Verification

Stitch uses compile-time assertions to guarantee size and alignment invariants:

#![allow(unused)]
fn main() {
const _: () = {
    assert!(core::mem::size_of::<OrderBookBlackboard>() == 64);
    assert!(core::mem::align_of::<OrderBookBlackboard>() == 64);
};
}

If a developer adds a field without adjusting padding, or if compiler alignment shifts, compilation fails immediately at build time with a clear error.

  2. Zero-Copy Views: stitch-wire can unpack frames directly from a borrowed byte slice (&'a [u8]) without allocating intermediate buffers on the heap.
  3. Payload Isolation: The header and payload are contiguous in memory, allowing zerocopy::FromBytes casting when structures are repr(C).

SIMD / SWAR Magic Byte Resynchronization

In streaming protocols (TCP streams or reassembled UDP packet buffers), network disruptions, byte-dropping proxies, or socket boundary splits can desynchronize the reader from frame boundaries.

stitch-wire implements high-speed SWAR (SIMD Within A Register) pattern matching to scan incoming byte streams and locate the 4-byte magic marker ("STCH") in single-digit nanoseconds.

1. The SWAR Technique

Scanning byte-by-byte (stream.windows(4)) in a scalar loop requires 4 load operations and branch evaluations per byte.

SWAR processes 8 bytes (a 64-bit word) per CPU instruction:

#![allow(unused)]
fn main() {
#[inline]
pub fn find_magic_swar(buf: &[u8]) -> Option<usize> {
    const MAGIC: u32 = u32::from_le_bytes(*b"STCH");
    let mut i = 0;

    // Process 8-byte chunks using 64-bit register arithmetic
    while i + 8 <= buf.len() {
        let chunk = u64::from_le_bytes(buf[i..i + 8].try_into().unwrap());
        
        // Fast-path check: check low and high 32-bit halves
        if (chunk as u32) == MAGIC {
            return Some(i);
        }
        if ((chunk >> 32) as u32) == MAGIC {
            return Some(i + 4);
        }
        
        // Advance by alignment boundary
        i += 4;
    }

    // Scalar fallback for remaining tail bytes
    while i + 4 <= buf.len() {
        if &buf[i..i + 4] == b"STCH" {
            return Some(i);
        }
        i += 1;
    }

    None
}
}

2. Benefits in Production

  • Throughput: Processes gigabytes of stream buffer per second without triggering L1 cache spills.
  • Resilience: Even if 1,000 corrupted bytes arrive over an unstable connection, the parser recovers framing immediately upon reading the next intact frame header.

Hardware-Accelerated Castagnoli CRC-32C

Data integrity is non-negotiable in financial trading, telemetry, and multiplayer gaming. However, software CRC calculations (such as traditional IEEE 802.3 CRC-32) can consume 5–10% of total pipeline CPU time.

stitch-wire utilizes the Castagnoli polynomial (0x1EDC6F41), which is natively accelerated in modern CPU silicon.

1. Why Castagnoli (CRC-32C)?

  1. Hardware Acceleration:
    • Intel/AMD x86_64 CPUs provide the dedicated CRC32 instruction (SSE4.2).
    • ARM64 CPUs provide the crc32c instruction via the ARMv8 Cryptography Extension.
  2. Superior Hamming Distance: For common network payload sizes (under 4 KB), Castagnoli provides significantly stronger error detection characteristics than standard IEEE 802.3 CRC-32.

2. Hybrid Implementation

stitch-wire selects the fastest available execution path at compile and runtime:

#![allow(unused)]
fn main() {
#[inline]
pub fn calculate_crc32c(data: &[u8]) -> u32 {
    #[cfg(target_arch = "x86_64")]
    {
        if is_x86_feature_detected!("sse4.2") {
            // SAFETY: Hardware instruction execution protected by runtime feature check
            return unsafe { hardware_crc32c_x86(data) };
        }
    }

    #[cfg(target_arch = "aarch64")]
    {
        // SAFETY: ARMv8 CRC extension
        return hardware_crc32c_arm(data);
    }

    // 256-entry precomputed Slicing-by-8 fallback table
    software_crc32c_sliced(data)
}
}

Measured Performance

  • Hardware CRC-32C: ~0.08 nanoseconds per byte (>12 GB/s on modern cores).
  • Software Slicing-by-8: ~0.4 nanoseconds per byte (>2.5 GB/s on older/embedded platforms).
  • Integrity: Any bit flip, burst corruption, or truncation is detected before payload bytes enter domain memory.

Vectored Scatter-Gather I/O

In high-frequency network applications, assembling a complete packet by copying the header and multiple payload slices into a single contiguous buffer is an unnecessary memory copy.

stitch-wire supports Vectored Scatter-Gather I/O, allowing the operating system kernel to directly gather distinct memory regions into a single network packet.

1. Zero-Copy Header & Payload Assembly

When dispatching a batch of messages:

  1. The Header resides in a small, stack-allocated or ring-allocated 28-byte array.
  2. The Payload resides in a separate columnar buffer or order book record.
  3. Rather than allocating a new Vec<u8> or performing memcpy, stitch-wire prepares a 2-segment IoSlice:
#![allow(unused)]
fn main() {
use std::io::IoSlice;
use stitch_wire::udp::pack_frame_vectored;

let header_buf: [u8; 28]; // Computed on stack
let payload_slice: &[u8]; // Borrowed from columnar compressor

let slices: [IoSlice; 2] = pack_frame_vectored(
    &mut header_buf,
    flags,
    seq,
    schema_hash,
    payload_slice,
);

// Dispatched via OS sendmsg / sendmmsg directly to the network NIC ring:
socket.send_vectored(&slices)?;
}

2. Kernel-Level Advantage

On Linux and modern OS kernels, sendmsg / sendmmsg with iovec writes memory directly to the Network Interface Card (NIC) transmit descriptors via DMA (Direct Memory Access).

This achieves true 0-copy transmission: zero heap allocations, zero user-space intermediate byte copies, and minimal cache pollution.

Streaming Adapters: Tokio & Std

To make stitch-wire seamlessly usable across diverse Rust runtimes, the ecosystem provides standalone adapter crates following the user-standard architecture established by ipatlas and statefs-rs.

  • Automatically handles partial TCP reads and fragmented packets.

2. Synchronous Blocking I/O: stitch-wire-adapter-std

Row-Oriented vs Columnar Data Layouts

Traditional serialization formats (JSON, MessagePack, Bincode, and Protobuf) encode records in Row-Oriented order (Array of Structures — AoS).

When transmitting or persisting large batches of homogeneous records (financial ticks, sensor feeds, or game state updates), row-oriented layouts severely limit compression ratios and throughput.

1. The Fundamental Compression Limit of AoS

Consider a tick structure:

#![allow(unused)]
fn main() {
struct Tick {
    timestamp: u64,
    price: f64,
    volume: u32,
}
}

In a row-oriented batch: [Timestamp 1, Price 1, Volume 1, Timestamp 2, Price 2, Volume 2, ...]

Adjacent bytes have completely different statistical properties: timestamps grow monotonically, prices fluctuate around a narrow decimal range, and volumes are discrete integers. Generic compressors (like gzip, zstd, or lz4) must maintain large sliding dictionary windows and struggle to find repetition across alternating types.

2. Columnar Transformation (SoA)

stitch-data restructures records into Structure of Arrays (SoA) batches:

Timestamps: [1000000001, 1000000002, 1000000003, ...]  -> Delta / Bitpacked
Prices:     [100.25,     100.26,     100.25,     ...]  -> Gorilla XOR Delta
Volumes:    [500,        500,        500,        ...]  -> Run-Length Encoding (RLE)

By grouping identical types contiguously:

  1. Domain-Specific Compression: Each column uses its optimal encoding algorithm (e.g. Gorilla for floats, RLE for repeating masks).
  2. Extreme Compression Ratios: Compression factors routinely reach 5x to 15x higher than row-oriented Protobuf or Bincode.
  3. SIMD Vectorization: Contiguous integer and float arrays can be processed directly by CPU vector registers (AVX2, AVX-512, ARM NEON).

Gorilla Delta-of-Delta Float Compression

Floating-point numbers (f32, f64) are notoriously difficult to compress with standard entropy or dictionary compressors because the IEEE 754 representation distributes sign, exponent, and mantissa across specific bit ranges. Small mathematical changes flip lower mantissa bits unpredictably.

stitch-data-transforms provides an optimized implementation of the Gorilla compression algorithm (originally designed by Facebook for time-series telemetry).

1. Mathematical Mechanics

Gorilla compresses a stream of floating-point values by computing the bitwise XOR between successive values:

$$\Delta_i = v_i \oplus v_{i-1}$$

  1. Identical Values: If $v_i = v_{i-1}$, $\Delta_i = 0$. This is stored as a single 0 bit.
  2. Similar Values: If $v_i$ is close to $v_{i-1}$, their sign and exponent bits are identical, causing $\Delta_i$ to have leading zeros and trailing zeros.
  3. Variable-Length Bitpacking:
    • If the leading and trailing zero count matches the previous XOR delta, write a 10 control bit followed by the meaningful bits.
    • If the zero counts differ, write a 11 control bit, the 5-bit leading zero count, the 6-bit meaningful length, and the meaningful bits.

2. Stitch Architecture Optimizations

The stitch-data-transforms implementation provides:

  • Zero Heap Allocations: Encodes directly into a caller-supplied byte slice using a zero-copy bitwriter (BitWriter).
  • f32 and f64 Support: Dedicated fast paths for 32-bit single-precision (used in game entity vectors) and 64-bit double-precision (used in financial asset prices).
  • Benchmark Performance: Compresses over 40 million floating-point numbers per second per core, achieving 60–80% size reduction on typical sensor and telemetry streams.

Run-Length Encoding (RLE) & SWAR Runs

Many real-world streams contain long sequences of identical repeated values:

  • Status flags and bitmasks (e.g. [1, 1, 1, 1, 1, ...]).
  • Visibility states in multiplayer game worlds.
  • Unfilled order quantity thresholds in market depth ladders.

stitch-data-transforms implements Run-Length Encoding (RLE) optimized with SWAR (SIMD Within A Register) for instantaneous run counting.

1. Encoding Format

Each continuous sequence of identical elements is represented as a (count, value) pair:

Input:  [42, 42, 42, 42, 42, 10, 10, 99]
Output: (5, 42), (2, 10), (1, 99)

The count is encoded using variable-length integer encoding (Varint) or fixed unsigned integers (u16/u32), ensuring minimal wire overhead for short runs while scaling smoothly to millions of identical items.

2. SWAR-Accelerated Run Detection

Instead of comparing array elements one by one, the encoder compares 64-bit blocks:

#![allow(unused)]
fn main() {
// Compare 8 bytes at a time
let word_a = u64::from_ne_bytes(slice[i..i+8].try_into().unwrap());
let repeated_word = value as u64 * 0x0101010101010101;

if word_a == repeated_word {
    // 8 identical elements confirmed in 1 CPU cycle
    count += 8;
    i += 8;
}
}

This approach allows RleEncoder to scan multi-megabyte buffers at memory bus speeds (>10 GB/s), delivering instantaneous compression on dense repetitive telemetry.

Dictionary Compression for Low Cardinality

In many domains, high-volume datasets contain values drawn from a very small set of distinct options (low cardinality):

  • Currency pairs and stock ticker symbols ("BTC-USDT", "ETH-USDT").
  • Entity archetypes and team IDs in games (TEAM_RED, TEAM_BLUE).
  • Geographic region codes and HTTP status codes.

stitch-data-transforms provides Dictionary Compression (DictEncoder / DictDecoder) to replace repeated strings or integers with compact integer indices.

1. Dictionary Mechanism

The dictionary operates in two phases:

  1. Dictionary Header: A compact table listing all unique symbols or values observed in the batch: ["AAPL", "GOOGL", "MSFT"] -> Indexes [0, 1, 2]
  2. Payload Indices: The original sequence is replaced by indices: ["AAPL", "AAPL", "MSFT", "GOOGL"] -> [0, 0, 2, 1]

When the cardinality is under 256 unique items, indices are stored as single bytes (u8), reducing a 16-character string symbol to a single byte on the wire (a 16x compression factor).

2. In-Memory Hashless Lookup

For hot paths, DictEncoder uses a fixed-size, stack-allocated direct-mapped table or linear cache to resolve index mappings without calling heap allocators (std::collections::HashMap).

Combined with stitch-data-derive, dictionary compression can be applied declaratively:

#![allow(unused)]
fn main() {
#[derive(ColumnarRecord)]
pub struct Trade {
    pub timestamp: u64,
    #[column(codec = "Dict")]
    pub symbol: &'static str,
    #[column(codec = "Gorilla")]
    pub price: f64,
}
}

Bitpacking & Dense Variable-Width Primitives

Standard hardware registers store integers in powers of two: 8, 16, 32, or 64 bits. However, domain values frequently occupy only a fraction of those bits:

  • Percentage values (0–100) require only 7 bits, yet consume 8 or 16 bits in standard memory structs.
  • Small delta timestamps (0–15 ms) require only 4 bits.
  • Integer values up to 1,000 require only 10 bits instead of 32 bits.

stitch-data-transforms provides Bitpacking (BitpackEncoder / BitpackDecoder) to pack arbitrary bit-width integers into continuous byte streams without wasting padding bits.

1. Bitpacking Mechanics

Given a sequence of $N$ integers where every element fits in $K$ bits:

Values (K=5 bits): [7, 12, 31, 2]
Binary: 00111, 01100, 11111, 00010

Packed stream:
Byte 0: 0 0 1 1 1 0 1 1  (7 + top 3 bits of 12)
Byte 1: 0 0 1 1 1 1 1 0  (bottom 2 bits of 12 + 31 + top 1 bit of 2)
Byte 2: 0 0 1 0 0 0 0 0  (remaining bits of 2 + zero padding)

Rather than using 16 bytes (four 32-bit integers), the payload consumes only 3 bytes — a 5.3x reduction in network bandwidth.

2. SIMD Acceleration

stitch-data-transforms leverages SIMD bit-shifting instructions to pack and unpack blocks of 32 values simultaneously.

Using AVX2/NEON instructions, unpacking runs at line rate (>15 GB/s), allowing decoders to reconstitute full integer arrays into CPU registers faster than standard DRAM can supply uncompressed data.

Schema Evolution & Compile-Time SCHEMA_HASH

Distributed systems evolve over time. Microservices are deployed independently, requiring protocol messages to remain backward and forward compatible.

stitch-data-core enforces a rigorous protocol governance model based on Field Descriptors, the SchemaCompatibilityVerifier, and Compile-Time SCHEMA_HASH Fingerprints.

1. Field Descriptors & Schema Definition

In stitch-data-core::schema, every message type exposes its schema contract:

#![allow(unused)]
fn main() {
pub struct FieldDescriptor {
    pub id: u16,
    pub name: &'static str,
    pub bit_width: u16,
    pub is_nullable: bool,
}

pub struct SchemaDefinition {
    pub schema_name: &'static str,
    pub fields: &'static [FieldDescriptor],
}
}

2. The Compatibility Contract

The SchemaCompatibilityVerifier evaluates evolution rules between a writer’s schema and a reader’s schema:

  • Subset Compatibility (Forward Evolution): A reader can safely parse data produced by a newer writer if all fields expected by the reader exist with compatible bit-widths. Extra fields in the writer’s schema are ignored.
  • Superset Compatibility (Backward Evolution): A writer with newer optional fields can produce messages readable by older consumers without binary deserialization crashes.
  • Type Safety: Any alteration to a field’s underlying bit width (e.g., changing u16 to u32 without an explicit field migration) produces a typed CompatibilityError::IncompatibleBitWidth.

3. The Compile-Time SCHEMA_HASH

To prevent mismatched schemas from being processed on hot paths, stitch-wire embeds an 8-byte schema_hash into every frame header:

#![allow(unused)]
fn main() {
// Calculated at compile time from field IDs, types, and sequence
pub const SCHEMA_HASH: u64 = 0xA4F2_8B19_3C00_E91D;
}

When a frame is received:

  1. The reader compares frame.schema_hash == Expected::SCHEMA_HASH.
  2. If the hashes match, zero dynamic schema verification is needed — the payload is unpacked in single-digit nanoseconds.
  3. If the hashes differ, execution branches into the fallback evolution decoder or yields a structured schema error before executing corrupt byte interpretations.

C-ABI Library & Panic-Safe FFI Boundaries

While the core Stitch ecosystem is authored in pure Rust, high-throughput systems frequently integrate with external ecosystems: C, C++, Python, Go, and legacy game engines.

stitch-wire-adapter-c exports a pure C-ABI dynamic and static library (.dll, .so, .dylib, .a) that allows any foreign language to produce and consume Stitch wire frames.

1. Safety & The Panic Boundary

Rust panics must never cross the foreign function interface (FFI) boundary. A panic unwinding into C or C++ stack frames results in undefined behavior and crashes the host process.

stitch-wire-adapter-c wraps every exported symbol with std::panic::catch_unwind:

#![allow(unused)]
fn main() {
#[unsafe(no_mangle)]
pub extern "C" fn stitch_unpack_frame(
    buf: *const u8,
    len: usize,
    out_frame: *mut StitchFrameView,
) -> i32 {
    let result = std::panic::catch_unwind(|| {
        if buf.is_null() || out_frame.is_null() {
            return -1; // Invalid pointer
        }
        
        let slice = unsafe { std::slice::from_raw_parts(buf, len) };
        match unpack_frame(slice) {
            Ok(frame) => {
                unsafe {
                    (*out_frame).version = frame.version;
                    (*out_frame).flags = frame.flags;
                    (*out_frame).payload_len = frame.payload.len() as u16;
                    (*out_frame).payload_ptr = frame.payload.as_ptr();
                }
                0 // Success
            }
            Err(_) => -2, // Malformed frame or CRC mismatch
        }
    });

    result.unwrap_or(-99) // Catch-unwind panic barrier
}
}

WebAssembly Linear Memory Zero-Copy Inspection

stitch-wire-adapter-wasm compiles to wasm32-unknown-unknown under strict #![no_std]. It operates directly on the WebAssembly instance’s linear memory without allocating intermediate JavaScript objects.

1. Linear Memory Architecture

When a browser worker receives binary WebSocket frames:

  1. The raw ArrayBuffer is copied directly into the WebAssembly instance’s linear memory.
  2. The JavaScript frontend invokes exported functions:
